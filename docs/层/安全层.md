# 安全层

安全层负责「谁登录了、是不是管理员、登出后 Token 还能不能用」。短信验证码本身在业务层发码；真正认 JWT、拦接口在这一层。

## 关键类

| 类 / 配置 | 作用 |
|-----------|------|
| `config.SecurityConfig` | 放行登录发码等白名单；其余 `/api/v1/**` 需认证；`/api/v1/admin/**` 需 `ROLE_ADMIN` |
| `security.JwtTokenProvider` | 签发 / 解析 JWT |
| `security.JwtAuthenticationFilter` | 从 `Authorization: Bearer` 取 Token；查 Redis 黑名单；写入 SecurityContext |
| `config.JwtProperties` | `jwt.secret`、`jwt.expiration-ms` |
| `config.MallProperties` | `mall.admin-phones`：登录时匹配则授予管理员 |

## 登录与角色

1. `POST /api/v1/auth/code`：业务层把验证码写入 Redis `login:code:{phone}`（TTL 约 2 分钟），并打日志。  
2. `POST /api/v1/auth/login`：校验验证码后删码；用户不存在则自动注册；签发 JWT。  
3. 手机号若在 `mall.admin-phones`（或环境变量 `ADMIN_PHONE`），响应里的用户角色为 `ADMIN`，Security 侧为 `ROLE_ADMIN`。  
4. `POST /api/v1/auth/logout`：把当前 Token 写入 Redis `jwt:blacklist:{token}`，过期时间与 Token 剩余寿命一致。  
5. Filter 每次请求先查黑名单，命中则视为未登录。

## 前后端分工

| 端 | 做什么 |
|----|--------|
| 前端路由 | `requiresAuth` / `requiresAdmin` 只是体验拦截；进后台会 `fetchMe` |
| 后端 | 最终权限；伪造前端角色无效 |

## 这一层不做什么

- 不对接真实短信网关  
- 不实现业务库存与订单状态机  
- 不把管理员手机号写死进前端代码（只配在服务端）
